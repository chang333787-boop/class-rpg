# 틱이 튀는 곳 — 출처 조사 (2026-09-20 · 마을 프로그램 담당 · **문서만 · 구현 전**)

> 보스: ⑤ 틱 튐(최악 53~55ms)의 출처를 재라 — 크롬북에서 아이가 제일 먼저 느끼는 것.
> 잰 법: 516명 판(물건 19,146) · 1366×610 · **CPU 6배 느리게** · `?sid=guest&dev=1` · 틱을 **한 번씩** 돌리며(`__tickBench(1)`) 그때의 ms·시각·길찾기 횟수(`__pathStats().호출` 차이)를 400~700번 기록. 규칙 수치·코드 수정 0(스위치는 재는 동안만 껐다 켰다).

## 한 줄
**튐은 '무엇이 무거워서'가 아니라 '언제 한꺼번에 하느냐'다.** 평소 틱은 2~3ms인데, **하루의 시각이 바뀌는 순간**(저녁 귀가 19~20시 · 자정 · 아침 5~10시) 한 틱에 **길찾기가 211~355번** 몰려 40~55ms가 된다. 지금 있는 '틱당 길찾기 예산'은 **리듬(출근·등교·귀가) 안에서만** 걸려서 이 몰림을 못 막는다.

## 왜 예산이 안 걸리나
`[MAC-TICKSPLIT]`(#668)의 틱당 길찾기 예산은 이렇게 걸린다:

```js
const budget = () => { const R = window.VRULES.tickSplit;
  if (!R.on || !TICKSPLIT.inRhythm) return true;      // ← 리듬(rhythmTick) 안일 때만 센다
  … if (TICKSPLIT.n >= R.rhythmBudget) return false; … };
```
- `TICKSPLIT.inRhythm` 은 **`rhythmTick`(출근·등교·귀가) 안에서만** true 다.
- 그런데 큰 판의 봉우리는 그 밖에서 온다 — **시각이 바뀌며 사람들이 제 목적지를 새로 잡을 때**(집으로·놀러·장 보러). 그 길찾기는 예산을 지나지 않는다.
- 그래서 예산을 8 → 3으로 줄여도 봉우리가 그대로였다(위 표).

## 값싼 수 (고르는 것은 보스 · 규칙·판정은 그대로)

| # | 수 | 효과(예상) | 치르는 것 | 크기 |
|---|---|---|---|---|
| A | **예산을 리듬 밖에도 건다** — 틱당 길찾기 상한 하나(예: 12번). 넘으면 그 사람은 **다음 틱에** 길을 찾는다(리듬이 이미 하는 방식 그대로) | 봉우리 225 → 12 → 가장 느린 틱이 평소(2~3ms)에 가까워진다 | 한꺼번에 출발하던 사람들이 **몇 틱에 걸쳐** 나뉘어 출발한다. 아이 눈에 "한 번에 우르르"가 조금 풀린다 — **연기 담당 확인 필요** | 작음(한 줄 + 수치) |
| B | 시각이 바뀔 때 **사람마다 몇 틱 흩뜨리기**(0~n틱 랜덤 지연) | 같은 효과 · 연기로는 더 자연스러울 수 있다 | 확률이 들어간다(우리 원칙상 조심 — 랜덤 대신 사람 번호 % n 으로 나누면 확률 없이 됨) | 작음 |
| C | 길찾기 자체를 싸게(A* 캐시·구역 단위 경로) | 봉우리 자체가 낮아진다 | 길찾기 코드를 손대야 한다 — 큰 일 | 큼 |

- **추천: A**(사람 번호로 나누는 B 와 함께면 더 좋다). 규칙·목적지는 그대로고, '언제 길을 찾나'만 나눈다.
- A 를 넣으면 **옛/새 같은 시드 표본이 달라질 수 있다**(출발이 한두 틱 밀리면 이후가 달라진다). 그때는 '표본 일치' 대신 **하루 뒤 인구·층·붐빔·일할 곳이 같은 범위인지**로 봐야 한다 — 보스 확인이 필요한 대목이다.

## 조심 · 안 한 것
- 맥북에서 CPU만 6배 느리게 한 값이다. 크롬북 GPU 는 따로다. 여기 숫자는 **CPU 쪽 튐**이라 그대로 읽어도 된다.
- 길찾기 호출 수는 `__pathStats().호출` 차이로 셌다(길 BFS 한 번 = 1).
- 어느 함수가 그 길찾기를 불렀는지까지는 **코드를 고치지 않고는 못 센다**. 스위치를 하나씩 꺼 좁혔고, 남은 봉우리가 리듬 밖이라는 것까지 확인했다.
- 규칙 수치는 안 건드렸다. 재는 동안만 스위치를 껐다 켰고, 코드 수정은 0이다.
