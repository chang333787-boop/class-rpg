## 1. 캐릭터 종이인형 (#175, CHAR-DOLL-1)

`성장rpg_svg\char\` 3차본 SVG 84장을 `assets/char/`로 넣고, 학생 캐릭터를 조각을 겹쳐 그린다.
합성 규칙 원본은 그 폴더 `README.md`의 **"합성 (코드)"** 절이고, 의사코드를 그대로 옮겼다.

### 구조 — `buildCharSVG`는 손대지 않는다

`docs/asset_implementation_spec.md` §4-A 준수. 새 입구를 만들고 호출부만 바꿨다.

```js
function charSVG(s) {
  if (CHAR_DOLL && _charDollReady) {
    const doll = buildCharDoll(s);
    if (doll) return doll;
  }
  return buildCharSVG(s);      // 예전 코드 그림 — 그대로 살아 있다
}
```

바꾼 호출부는 3곳뿐: `renderCharCard` · 전투 화면 · 학생 목록.

### 폴백 3단

| 단계 | 조건 | 결과 |
|---|---|---|
| 1 | `CHAR_DOLL = false` | 항상 예전 그림 (되돌리기 스위치) |
| 2 | 에셋 로드 전/실패 | 예전 그림 (로드되면 `renderAll()` 1회로 교체) |
| 3 | `base_{charType}` 없음 | 그 학생만 예전 그림 |
| — | 장비 파일 하나만 없음 | **그 슬롯만 생략**, 나머지는 정상 |

### 슬롯 매핑

착용 데이터는 **`s.equipmentIds`** 다(`s.equip` 아님). 값이 없거나 `'none'`이면 건너뛴다.

| 데이터 | 파일명 | id 범위 | 장수 |
|---|---|---|---|
| `s.charType` (1~4) | `base_{n}.svg` | 1·2·3·4 | 4 |
| `equipmentIds.body` | `body_{id}.svg` | `e_b1`~`e_b30` | 30 |
| `equipmentIds.head` | `head_{id}.svg` | `e_h1`~`e_h10` | 10 |
| `equipmentIds.glove` | `glove_{id}.svg` | `e_g1`~`e_g10` | 10 |
| `equipmentIds.shoe` | `shoe_{id}.svg` | `e_s1`~`e_s10` | 10 |
| `equipmentIds.weapon` | `weapon_{id}.svg` | `e_w1`~`e_w10`, `e_ws1`~`e_ws10` | 20 |

로딩은 로그인 직후(`enterGame`) 84장 일괄 fetch → `inner()`로 바깥 `<svg>` 벗긴 문자열 캐시.
**실측 183KB.** (`du`가 407K로 보이는 건 디스크 할당량이다. 용량 판단할 때 속지 말 것.)

### ⚠️ 함정 — 정규식을 JS **문자열**로 만들 때

```js
// ✗ 이렇게 쓰면 [\s\S] 가 [sS] 로 죽는다 (문자열 안에서 \s 는 그냥 s)
new RegExp('<g class="' + cls + '">[\s\S]*?</g>')
// ✓ 문자열이면 백슬래시를 두 번
new RegExp('<g class="' + cls + '"[^>]*>[\\s\\S]*?<\\/g>')
```

정규식 **리터럴**(`/[\s\S]/`)은 한 번이면 되지만, `new RegExp('...')`는 문자열이라 두 번이다.
이걸 놓치면 **에러 없이 조용히** 그룹 추출이 실패해서 손가락·머리카락이 어긋난다.
하네스 돌리기 전에 잡았다. 다음에 `new RegExp` 쓸 때 같은 자리에서 또 밟기 쉽다.

### rebase 때 캐시버스터 충돌 — 네 가지 함정

캐시버스터는 여러 브랜치가 **같은 줄**을 동시에 만지는 거의 유일한 자리다. 그래서 rebase 사고가 여기 몰린다.
날짜순으로 넷을 겪었고, 넷 다 **에러가 안 난다**는 공통점이 있다.

**① `git checkout --ours <파일>` 은 그 파일 *전체* 를 HEAD로 되돌린다.**
충돌 난 줄만이 아니다. **충돌이 없던 내 변경까지 같이 사라진다.**
#204에서 gamedata 캐시버스터(d→e)가 그렇게 날아갔고, `smoke`가 34/0 → **31/3**으로 떨어져서 발견했다.
기준선을 안 돌렸으면 gamedata가 옛 캐시로 배포됐을 것이다.
→ `--ours`/`--theirs`를 쓴 뒤에는 **그 파일에 내 변경분이 남아 있는지 따로 확인**한다.

**② 한 충돌 블록에 남의 파일 줄이 같이 들어온다.**
예를 들어 `smoke-test.mjs`의 `student.js` 줄과 `admin.css` 줄이 한 블록에 묶인다.
여기서 기계적으로 자기 브랜치 쪽을 고르면 **남이 방금 올린 `admin.css` 버전을 되돌려 놓는다.**
에러도 안 나고 교사 화면이 낡은 CSS를 문다(#189).
→ 충돌 블록은 **HEAD 쪽으로 채택**하고, **자기 파일의 값만** 새 값으로 다시 적는다.

**③ (#205 이후) 캐시버스터는 html 한 곳만 고친다.**
`scripts/smoke-test.mjs`가 이제 html의 `src`/`href`를 읽어 쓴다. 손으로 적는 목록이 없다 —
**smoke의 목록·맵을 고치지 말 것.** ①②가 나던 자리 자체가 사라졌다.
단, `gamedata.js`·`curriculum.js`처럼 **여러 html이 쓰는 파일은 `student.html`·`admin.html`·`kiosk.html` 세 곳을 같이** 올려야 한다.
빠뜨리면 새 검사가 FAIL로 잡는다(전에는 REVIEW라 최종 결과를 안 막고 지나갔다).

**④ 충돌이 안 났다고 버스터가 맞는 것은 아니다.**
③의 새 검사로도 못 잡는 구멍이 하나 남는다. #206에서 실제로 걸릴 뻔했다.
내 브랜치가 `gamedata.js?v=...f`로 올렸는데, 그 사이 머지된 #207도 **같은 f**를 썼다.
값이 같으니 **충돌이 안 나고 조용히 자동병합**된다. 그런데 내 브랜치는 `gamedata.js`의 **내용**을 바꾼다 —
버스터는 그 새 내용을 가리키지 못한다. 새 검사는 세 html이 서로 **일치**하는지를 보므로 **셋 다 f면 통과한다.**
충돌도 FAIL도 없이 옛 캐시로 배포될 뻔했다.
→ **rebase 후에는 바꾼 파일마다 버스터가 main 값보다 앞서는지 눈으로 확인한다.**

```bash
# 내 브랜치와 main의 버스터를 나란히 보기
for f in student.html admin.html kiosk.html; do
  echo "== $f"; git show origin/main:$f | grep -o './[a-z_]*\.\(js\|css\)?v=[0-9a-z]*'
done
```

**그리고 넷 모두에 공통으로:** rebase 뒤에는 `verify-safety`와 `smoke-test` 기준선을 **반드시 재실행**한다.
형식이 아니라 위 넷을 잡는 장치다 — ①은 실제로 그렇게 잡혔다.

## 4. 작업 위치 규칙

- **메인 clone(`C:\Users\USER\projects\class-rpg`)은 `main`에 둔다.** 여기서 브랜치를 만들지 않는다.
- 작업은 **worktree**에서 한다: `git worktree add ../class-rpg-wt-<이름> -b <브랜치> origin/main`
- 여러 세션이 동시에 돈다. 메인 clone에서 브랜치를 갈아타면 **남의 작업 트리를 흔든다.**
  (실제로 하루 중 메인 clone이 `feat/deco-svg-16` · `fix/balance-b1-b2`로 옮겨가 있던 때가 있었다.)
- 머지 확인되면 worktree와 로컬 브랜치를 정리한다. 브랜치 삭제는 **`-d`만** 쓴다(`-D` 금지).
- `.claude/launch.json`은 세션들이 공유한다. **덮어쓰지 말고 자기 항목만 추가**할 것
  (한 번 통째로 덮여서 다른 세션 설정이 사라진 적 있다).
