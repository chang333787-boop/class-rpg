# 우리 마을 저장 v3(층) — 코드 기준 검증 한 장 (2026-09-20 · 구현 금지 · 월요일 학교 보스와 맞출 안건)

> 대상: 보스 설계안 `docs/placement_classes_design_20260919.md` §4 "구역마다 층별 문자열 `{g,p,o,s,e}`". 기준 코드: `feat/village-45` 09-20 머지본(59차 + MAC/DESIGN).
> **결론 먼저 — 방향은 맞다. 모양 두 가지만 바꾸자: ① 구역 값은 객체가 아니라 *문자열 하나*로 ② `cells` 를 층별로 쪼개지 말고 *옆에 배열을 더한다*. 그러면 sync.js·규칙·백업·교사 탭을 안 건드리고, 닿는 함수가 51개 → 약 12개로 준다. 그리고 가장 큰 위험은 서버가 아니라 *옛 캐시를 든 기기*다.**

## ⓐ `cells` 를 층별 배열로 바꾸면 닿는 곳
- `cells` 를 만지는 함수 **51개**(+ 시험 훅 19개) · 직접 색인 `cells[` **85곳** · `cells.forEach` **29곳**. 많이 만지는 순: `loadSaved`(12) · `tickFolks`(6) · `canPlace`(4) · `removeAt` · `pickDestination` · `syncFolks`(3) · `amenityOf` · `updateGhost` · `act` · `overlayFor` · `jobsTick` · `rhythmTick` · `visitorGoal` …
- 거의 전부 "이 칸에 **무엇이 있나**"를 한 값으로 읽는다(`isRoad`, `K[c.k].need`, `rec.root === i`). 통째로 층 배열로 바꾸면 51개를 다 고쳐야 하고 월요일 3-way 병합과 정면으로 부딪힌다.
- **대안(추천): `cells` 는 그대로 '길 또는 물건' 층으로 둔다**(길과 물건은 지금도 앞으로도 서로 배타적이다). 새 층은 **옆에 배열을 더한다**: `ground[]`(땅) · `side[]`(길가 물건 — 길 칸에만) · `edges`(테두리). 기존 51개 함수는 그대로 돌고, 닿는 곳은 `canPlace` · `placeAt` · `removeAt` · `encodePlot`/`decodePlot` · `serialize`/`loadSaved` · `buildChunk`(또는 `paintBoard`) · `amenityOf` · `computeSat` · `updateGhost` · `act`/`paint*` — **약 12개**.
- 땅으로 옮길 종류는 **작게 시작**: 잔디밭·자갈길·꽃밭(1×1, 기능이 가볍다). **광장·연못은 물건 층에 남긴다** — 광장은 축제(`plazaRoot`·`eventTick`)·필요 '놀이'·손님 볼거리가, 연못은 필요 '물'이 `cells` 를 읽는다. 설계안의 "포장 위 화분"은 광장을 땅으로 옮기는 2차에서.

## ⓑ v2 → v3 읽기 변환은 기존 저장본을 100% 되살리나 — **그렇다**
- v2 는 한 칸 한 물건이라 땅 종류와 물건이 **겹친 적이 없다** → 종류로 갈라 담기만 하면 손실 0. 구역 문자열은 root 칸만 적고 위치는 순서로 정하므로(`encodePlot`) 층마다 **같은 인코딩을 그대로** 쓴다. `palette`(뒤에 붙이기만)·`houses`·`signs`(root 칸 번호가 키)는 그대로.
- 지켜야 할 것: 원문을 `.backup` 에(v1→v2 와 같은 예의) · 복원 때는 `on` 검사를 건너뛴다(PR #458 이 이미 그렇게 한다 — 옛 마을을 말없이 버리지 않는다).
- 검증 방법(구현 때): v2 저장본 N개를 v3 로 읽어 → `__snapshot()` 의 물건 목록이 v2 로 읽은 것과 **완전히 같은지** 대조(탭 PR #438 에서 쓴 방식).

## ⓒ sync.js · keepalive · 교사 탭 · 백업/복원에 미치는 영향
| 곳 | 구역 값이 **객체** `{g,p,o,s,e}` 면 | 구역 값이 **문자열 하나**면(추천) |
|---|---|---|
| `sync.js` `hash(snap.plots[k])` | **깨진다** — `s.length`·`charCodeAt` 가 문자열을 가정(67·106·112줄). `fromVillage`/`toVillage` 도 손봐야 함. `node scripts/village-sync/test.mjs` 32건 재작성 | **변화 0** |
| Firebase 규칙(`classRPG_villages`) | 원문이 학교 PC 에만 있어 **확인 불가**. 구역 값을 문자열·길이로 검사하고 있다면 객체는 **거절**된다 | 그대로 통과(길이 상한만 확인) |
| 닫힐 때 keepalive 60KB | 영향 없음 | 영향 없음 — 한 구역 가득(놓은 것 419) 저장본 **전체가 3.5KB**. 층이 늘어도 구역당 1~2KB |
| 교사 탭(`admin.js`) | `plots?shallow=true` 로 **키만** 센다 → 변화 0 | 변화 0 |
| `village-backup.mjs` · `village-restore.mjs` | 구역을 통째로 옮긴다(값 모양 안 봄) → 변화 0 | 변화 0 |
- **추천 모양:** `plots/<px_py>` = `"<물건·길 층>|g<땅 층>|s<길가 층>|e<테두리 층>"`. 구분자 `|` 는 지금 인코딩 문자(`A-Za-z0-9-_~.`)에 없다. 빈 층은 아예 안 쓴다 → **층이 없는 구역의 문자열은 v2 와 글자 하나 안 다르다**(그 구역은 다시 올리지도 않는다).
- 단점: 한 층만 바뀌어도 그 구역 전체를 다시 보낸다(1~2KB — 지금도 구역 단위라 같다).

## ⓓ 주민 길찾기·필요 판정은 길 층만 보면 되나 — **절반만 맞다**
- **길찾기는 맞다**: `isRoad(i)` → `roadBFS` → 전부 길만 본다. 길가 물건은 `cells` 밖(`side[]`)이라 **걷기를 안 막는다** — 고칠 것 없음.
- **필요 판정은 아니다**: `computeSat`·`needBeside`·`buildingBeside`·`pickDestination` 의 볼일 칸은 길 칸의 **이웃 칸에 있는 것**의 `need` 를 읽는다. 필요를 가진 종류가 **땅에도(꽃밭=쉼) 길가에도(긴의자·짧은 의자=쉼)** 있다 → 이웃 칸의 `cells` **와** `ground`·`side` 를 다 봐야 한다. 주변 가치(`amenityOf`, F33)도 같다.
- 길가 물건은 **그 길 칸 자체**가 필요를 채우는 셈이라 판정이 오히려 자연스러워진다(의자 앞 길 칸에서 쉰다).

## ⓔ 그리기 — draw call·삼각형 예상
- `buildChunk` 는 청크(4×4칸) 안의 모든 부위를 **재질 통 2개**(lit·glass)로 합친다 → **층이 늘어도 draw call 은 안 는다**(지금 한 구역 가득 90).
- 삼각형은 **겹친 만큼만** 는다: 나무 밑 잔디 +2, 꽃밭은 DESIGN-TILE-1(#433) 모양 그대로. 더 싸게: 잔디·자갈은 **판 바탕 그림**(`paintBoard` 캔버스)에 칠하면 삼각형 **0**.
- 길가 물건은 길 칸마다 하나라 지금 물건 수와 같은 규모. 테두리는 변마다 얇은 상자 1개(≈12 삼각형) — 구역 둘레를 다 둘러도 128변 ≈ 1.5k. 예산(삼각형 ≤150k · 지금 121k) 안.

## 보스 판단 "서버 저장(#214) 전에 v3 를 정하면 옮길 데이터가 localStorage 뿐" — **맞다, 단 더 급한 위험이 따로 있다**
- 맞는 부분: 규칙 게시 뒤엔 서버 데이터·`.validate`·32건 시험이 v2 에 묶인다. **문자열 하나 모양이면 그 묶임 자체가 없어져** 서버 저장 뒤에 해도 된다 → 서두를 이유가 준다.
- **진짜 위험 = 옛 캐시 JS.** 마을 html 은 **캐시버스터가 없다**. 옛 판(`SAVE_V=2`)이 v3 저장본을 열면 `loadSaved` 가 "모르는 저장본 버전"으로 **`.broken` 에 치우고 기본 판으로 시작** → 곧 저장 → 서버 저장이 켜져 있으면 **기본 판이 서버를 덮는다.** `.broken` 은 2만 자까지만 남긴다.
  → **두 걸음으로 낸다:** ① *읽기만 하는 판* 먼저(v3 를 읽을 줄 알되 **쓰기는 v2**) — 한 주 돌린다 ② 그 뒤 *쓰는 판*. **`v` 를 안 올리고 슬쩍 넣는 길은 안 된다** — 확인해 보니 옛 `decodePlot` 은 끝 표시가 없어 `|` 뒤 글자를 두 자씩 **엉뚱한 종류·자리로 읽는다**(없는 물건이 생길 수 있다). 그러니 버전은 올리되(`v:3`), **읽기 판이 충분히 퍼진 뒤에만** 쓰기 판을 낸다.
- 같은 이유로 **학교 PC 판(65차+)이 저장 형식을 이미 건드렸는지**를 월요일에 제일 먼저 확인한다(`SAVE_V`·`encodePlot`).

## 덧붙임 — 꽃밭처럼 색이 여러 개인 종류는 어떻게 담나 (보스 질문 09-20)
- **색마다 kind id 를 따로 두는 쪽이 안전하다**(예: `flowerB_red`·`flowerB_yellow`). 칸 하나의 값은 12비트(`palette 번호 × 4 + 방향`, 글자 둘)라 **palette 는 1,024종까지** 들어가고, palette 는 뒤에 붙이기만 하므로 색이 수십 개 늘어도 **문자열 길이·옛 저장본·sync.js 가 그대로**다.
- **색을 칸 속성으로** 두려면 칸 값에 비트를 더 써야 한다 = 인코딩이 바뀐다 = v3 와 같은 위험(옛 판이 못 읽음). 방향 2비트를 색으로 돌려쓰는 꼼수는 돌릴 수 있는 종류에서 깨진다. → **하지 않는다.**
- 화면은 저장과 따로다: K 에 `variantOf: 'flowerB'`·`tint: '#e0457b'` 같은 **규칙 필드**를 두면 트레이는 **카드 1장 + 색 점 6개**로 묶어 보여 줄 수 있다(같은 `variantOf` 끼리 한 카드, 마지막에 고른 색을 기억). 목표·필요·꾸미기 점수는 `variantOf` 로 묶어 센다(`countKind('flower')` 가 색마다 흩어지지 않게). 이건 저장을 안 건드리는 프로그램 작업이라 디자인 담당이 id 목록을 주면 바로 할 수 있다.

## 월요일에 정할 것 (셋)
1. 구역 값 모양: **문자열 하나(`|` 구분) — 추천** vs 객체.
2. 코드 모양: **`cells` 유지 + 배열 더하기 — 추천** vs 층별 배열로 전면 교체.
3. 내는 순서: **읽기 판 → (한 주) → 쓰기 판**, 땅은 잔디·자갈·꽃밭부터. 그 전까지는 저장을 안 건드리는 1단계(PR #458 `on` 자리)와 입력·규칙 작업을 한다.
